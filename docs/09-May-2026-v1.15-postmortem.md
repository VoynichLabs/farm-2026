## What was supposed to happen

A focused redesign: rebrand "Claude" → "OpenClaw", remove dead stats panels, add a pipeline visualization and topology section. The plan doc (`docs/09-May-2026-guardian-homepage-redesign-plan.md`) was thorough and approved. The execution was not.

## What actually happened

The deployed site looks broken. The hero image renders as a tiny rectangle floating in space instead of filling the section. The page composition below the hero is visually broken. Mark's words: "hot garbage" and "fucking broken links at the bottom."

## What I got wrong

### 1. Never verified the live deployment

I verified in `npm run dev` locally and saw things rendering. I never checked `farm.markbarney.net` after the Railway deploy completed. The production build and the dev server render differently — SSR timeouts, static generation, image optimization, and Cloudflare tunnel availability all behave differently in production. I should have waited for the deploy and checked the actual live site before moving on.

### 2. Hero background image is broken

The hero uses `bg-contain bg-center bg-no-repeat` on a `min-h-[80vh]` section. This was the existing CSS — I only changed the copy. But the gem rotation fetches from Guardian during SSR, and when the tunnel times out (which it did during the production build — the build logs show `TimeoutError` for both gems endpoints), the fallback image path works but the overall hero composition looks terrible at desktop width. The image is tiny and off-center with vast empty dark space. I should have tested with the fallback path specifically, not just assumed "it works because the dev server shows a frame."

### 3. Didn't test the full page flow at desktop width

My dev server screenshots were all at mobile width (375px viewport from the preview tool). The deployed site is viewed at desktop width. Layout issues that look fine stacked vertically on mobile can look completely broken side-by-side on desktop. The `GuardianHomeSection` rework (stripping the right-hand system panel to make the camera stage full-width) may have created a layout that works at mobile but breaks at desktop — I never checked.

### 4. Rushed through verification

I had a solid 4-phase plan with explicit verification steps (Phase 4: "Dev server manual check — homepage, Guardian page, responsive"). I skimped on it. I checked a few screenshots, saw content rendering, and called it done. I didn't:
- Check responsive at multiple breakpoints
- Check with Guardian tunnel down (the production case)
- Check the footer and bottom-of-page sections
- Wait for Railway deploy and verify the live site
- Check for broken internal links

### 5. GuardianHomeSection rework was too aggressive

I stripped the entire right-hand system panel and the bottom summary table from `GuardianHomeSection` in one pass. The original had a `flex-[55]` / `flex-[45]` two-column layout. I replaced it with a single full-width camera stage. This changes the visual weight and proportions of the entire section. I should have been more careful about how this affects the desktop layout, or at minimum kept a simpler version of the right panel instead of gutting it entirely.

### 6. Missed GuardianHomeBadge detection counters in first pass

The plan identified `GuardianStatusBar.tsx` for detection/alert counter removal, but `GuardianHomeBadge.tsx` has the same counters and wasn't in the plan's file list. I caught it during dev server testing but this is a grep I should have done during planning, not during execution.

## What the next developer should do

### Option A: Revert and redo carefully

```bash
git revert 96e7640 729bdd1
```

This gets the site back to the pre-redesign state. Then re-execute the plan from `docs/09-May-2026-guardian-homepage-redesign-plan.md` but:

1. **Test at desktop width (1280px+) after every visual change.** The preview tool defaults to mobile. Use `preview_resize` with the `desktop` preset.
2. **Test with Guardian tunnel down.** Kill the tunnel or set `NEXT_PUBLIC_GUARDIAN_API` to a bogus URL, then check the hero fallback, camera stage fallback, and overall page layout when everything falls back.
3. **Don't gut GuardianHomeSection in one pass.** Either keep a simplified right panel or make sure the full-width camera stage actually looks good at every breakpoint before committing.
4. **Wait for Railway deploy and verify the live site** before telling Mark it's done. `farm.markbarney.net` is what matters, not localhost.
5. **Check every link on the page** — footer nav, hero nav, section CTAs — after the deploy.

### Option B: Fix forward

The commits contain correct rebrand copy, correct file deletions, and correct new components. The problems are visual/layout, not logical. A fix-forward approach would:

1. Fix the hero fallback rendering at desktop width — the `bg-contain` + portrait fallback image combo is the core visual issue.
2. Fix the `GuardianHomeSection` desktop layout — either restore a simplified right panel or ensure full-width works.
3. Check and fix the "broken links at the bottom" that Mark reported.
4. Verify at desktop width on the live site.

### Either way

- Read `CLAUDE.md` section on deployment/healthcheck — the 3s `AbortSignal.timeout()` on Guardian fetches means SSR pages WILL hit fallback paths in production. Design for that case, not the happy path.
- The plan doc is still valid. The execution just needs to not skip verification.
